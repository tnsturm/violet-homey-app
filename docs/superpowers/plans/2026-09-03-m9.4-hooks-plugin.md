# M9.4 — Framework-Hooks als Plugin (B1) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this
> plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Warum `executing-plans` und nicht `subagent-driven-development`** (CLAUDE.md §0): alle Tasks
> teilen denselben Toolchain-State — zwei `node --test`-Suiten (Plugin + VioletApp), EIN Satz
> Hook-Dateien, der nur den Ort wechselt, und eine gemeinsame Fehlerliste (ein Hook, der im
> Plugin-Pfad nicht auflöst, zeigt sich nur im Live-Test am Ende). Frische Subagent-Kontexte
> müssten jeweils beide Repos neu lesen.

**Goal:** Die generischen Gate-Hooks existieren genau einmal — im `agentic-loop-framework`-Plugin
(`plugin/hooks/hooks.json`, Pfade über `${CLAUDE_PLUGIN_ROOT}`) — und VioletApp bezieht sie von
dort. In `VioletApp/.claude/hooks/` bleiben nur Homey- und projektspezifische Hooks. Drift bei den
migrierten Hooks ist damit strukturell null; Checkpoint-Schritt 7a gilt für sie nicht mehr.

**Architecture:**
- **Plugin-Runtime** `plugin/hooks/` (Hook-Skripte + `lib/`) + `plugin/hooks/hooks.json`
  (Registrierung, gleiche `if`-Filter wie VioletApp seit M9.0 Block b) + `plugin/test/hooks/`
  (Smoke-Tests, `plugin/package.json` mit `node --test test/`).
- **Scoping-Guard** (der eine neue Baustein): Claude Code lädt Plugin-Hooks user-weit, ein
  Per-Projekt-Opt-in einzelner Plugin-Hooks gibt es nicht (nur `enabledPlugins` ganz/gar nicht,
  Doku-Recherche 2026-09-03). Jeder Plugin-Hook prüft deshalb als Erstes `lib/opt-in.js`:
  angeschaltet, wenn die Settings-Kaskade des Projekts (`.claude/settings.json`,
  `.claude/settings.local.json`, lokal gewinnt) `enabledPlugins["agentic-loop-framework@skill-agentic-loop-framework"] === true`
  trägt — dasselbe native Feld, das `claude plugin install --scope project` schreibt. Sonst
  `exit 0` ohne Prüfung. Test-Harnesse setzen `AGENTIC_LOOP_HOOKS_FORCE=1` (Fixture-cwds haben
  keine Settings). Die PRÜF-Logik der Hooks bleibt unverändert (SCOPE-NEGATIV).
- **Libs bleiben doppelt** (`plugin/hooks/lib/` für Plugin-Hooks, `templates/.claude/hooks/lib/`
  für projektlokale Hooks wie `stop-verify`/`docs-header-guard`): Projekt-Hooks kennen den
  Plugin-Pfad nicht. Ein Plugin-Test (`lib-drift.test.js`) hält beide Kopien EOL-normalisiert
  byte-gleich — Drift ist damit mechanisch statt manuell geprüft.
- **Templates** verlieren die migrierten Hook-Kopien; das Template-`settings.json` registriert
  nur noch projektlokale Hooks und setzt den `enabledPlugins`-Eintrag.

**Tech Stack:** Node.js (CommonJS, keine Runtime-Deps), `node:test`, Claude Code 2.1.241
Plugins (`hooks/hooks.json`, `${CLAUDE_PLUGIN_ROOT}`, `--plugin-dir` für den Live-Test), Git
Worktrees: VioletApp `.claude/worktrees/m9.4-hooks-plugin` (Branch `worktree-m9.4-hooks-plugin`
auf `origin/main` 606d0c0), Framework `.worktrees/m9.4` (Branch `m9.4-hooks-plugin` auf 0.1.36).

## Global Constraints

- **Keine neuen Runtime-Dependencies**, keine Änderung der Hook-Prüflogik, kein
  Violet-Versionsbump. Eine Dev-Dependency nur im Plugin-Test-Harness: `typescript@^5.9.3`
  (`plugin/package.json`, ausschließlich für den typecheck-gate-Smoke-Test, der ein echtes
  `tsc` braucht). Existenznachweis: npm-Registry-Paket `typescript` (Microsoft), in VioletApp
  bereits unter dem Alias `typescript-checkjs` im Einsatz; der `package-guard`-Hook hat den
  Write der Manifestdatei am 2026-09-03 mit Registry-Lookup passieren lassen (kein Block).
  Nachgetragen nach dem Conventions-Review (CLAUDE.md §5) — ursprünglich stand hier fälschlich
  „keine neuen Dependencies".
- **Hooks bleiben fail-open auf eigene Fehler**; der Opt-in-Guard ist ein zusätzlicher
  `exit 0`-Pfad, nie ein Block.
- **Nicht pushen** — §9: `/code-review` auf beide Diffs, dann Push-/PR-Frage stellen.
- **Migrationsumfang** (Kandidatenliste B1 inkl. beider Kandidaten, Drift-Analyse: Logik
  identisch, nur Kommentartext weicht ab): `test-gate`, `typecheck-gate`, `commit-msg-guard`,
  `package-guard` (+ `lib/package-specs`), `control-bytes-guard`, `dashboard-guard`,
  `run-matching-test`, `selftest-guards`, `handoff-notice`. Bleiben in VioletApp:
  `secrets-guard`, `compose-guard`, `release-gate`, `check-version-sync`, `changelog-lang-guard`,
  `json-guard`, `stop-verify`, `docs-header-guard`, `lib/{log,in-repo,env-ready,spawn-env,changelog}`.
- **NO-ACTION-Bedingung geprüft:** Scoping IST per Guard lösbar (s. o.) → Migration wird
  vollständig durchgeführt, Zwischenschritt-Alternative entfällt.
